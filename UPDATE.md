# Attest0 — установка, обновление, откат

Инструкция для того, кто обслуживает боевой сервер. Все команды — как
есть, выполнять по порядку. Ничего в голове держать не нужно: если
скрипт на каком-то шаге упал — увидите цветное сообщение об ошибке и
что делать дальше, скрипт до этого места ничего разрушительного не
успел.

Где всё лежит на сервере: `/opt/attest0` (если ставили install.sh со
значениями по умолчанию). Дальше в примерах — все команды выполняются
из этой папки.

```bash
cd /opt/attest0
```

## 1. Первая установка

Нужен чистый сервер Ubuntu/Debian с правами root и белым IP,
привязанным к домену (A-запись `attest0.ru` → IP сервера, настраивается
у регистратора домена/DNS-провайдера — до установки).

```bash
curl -fsSL https://raw.githubusercontent.com/32syntax/attesto-deploy/main/install.sh | sudo bash
```

Скрипт спросит домен, email (для Let's Encrypt) и владельца GitHub
с образами — дальше всё делает сам: ставит Docker, если его нет,
генерирует пароль базы данных и секретный ключ (никто их руками не
придумывает и не хранит в переписке), скачивает и запускает контейнеры.

**После установки — обязательно, иначе письма не будут уходить:**
откройте `/opt/attest0/.env` и заполните блок SMTP (реальный
почтовый сервер, не тестовый).

**Про оплату.** ЮKassa не выдаёт ключи магазина, пока нет живого сайта
с публичной офертой и политикой обработки данных — то есть в момент
первого запуска ключей ЮKassa быть ещё не может (курица и яйцо). Из-за
этого по умолчанию (`PAYMENT_PROVIDER=stub`) боевая система принимает
**только оплату по счёту** (банковский перевод, подтверждается вручную
в `/platform` после сверки с выпиской) — заполните
`INVOICE_PAYEE_NAME/INN/ACCOUNT/BANK` в `.env`, без этого backend
откажется стартовать в боевом режиме (защита от запуска с пустыми
реквизитами, см. `backend/config.py` → `assert_production_safe`).
Онлайн-оплата картой в этом режиме на backend'е тоже отключена явно
(`create_checkout` и вебхук `/webhooks/payments/stub` возвращают
ошибку в `ENVIRONMENT=production`) — не просто скрыта в интерфейсе, а
не работает на уровне API, так что это безопасно само по себе.

Когда сайт заработает и вы получите ключи ЮKassa — впишите
`PAYMENT_PROVIDER=yookassa`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`
в `.env` и перезапустите (`docker compose ... up -d`) — онлайн-оплата
включится, оплата по счёту продолжит работать как раньше (это два
независимых способа оплаты, не взаимоисключающих).

После правки `.env`:

```bash
docker compose -f docker-compose.prod.yml --env-file .env up -d
```

## 2. Как понять, что вышло обновление

Новые версии публикуются как теги/релизы в GitHub-репозитории проекта
(`vX.Y.Z`, например `v0.24.3`) — там же в `CHANGELOG.md` видно, что
изменилось. Смотрите страницу Releases репозитория. Версия — то же
число, что в `frontend/package.json` на момент релиза.

## 3. Обновление

Одна команда, версию берём со страницы Releases:

```bash
cd /opt/attest0
./update.sh 0.24.3
```

Что скрипт делает **по порядку** (это всё видно в выводе, с пометками
«Шаг N/6»):

1. **Бэкап базы данных** — снимок сохраняется в `backups/` рядом,
   имя файла содержит версию и время. Если бэкап не снялся — скрипт
   останавливается, ничего дальше не трогает.
2. Запоминает текущую версию — чтобы `rollback.sh` знал, куда
   возвращаться.
3. Переключает версию образов в `.env`.
4. Скачивает новые образы. Если скачать не удалось (сеть, версия не
   существует, опечатка) — откатывает `.env` обратно и останавливается,
   контейнеры не трогает, всё продолжает работать на старой версии.
5. Прогоняет миграции базы данных и сид справочника (роли, права,
   тарифные редакции — идемпотентно, не трогает организации/данные
   клиентов), пересоздаёт контейнеры (`backend`, `celery-worker`,
   `frontend`) на новых образах — база данных (`db`) и очередь
   (`redis`) не перезапускаются, соединения не рвутся.
6. Ждёт до 60 секунд, пока backend пройдёт проверку здоровья
   (`/api/v1/ready`). Если не прошёл — предупреждает и советует
   `./rollback.sh`, но версию в `.current_version` не подтверждает.

Пока скрипт не написал `Готово` — старая версия либо ещё работает,
либо разница минимальна (миграции применяются в течение нескольких
секунд). Ощутимого простоя (когда сайт совсем не открывается) быть не
должно — старые `backend`/`frontend` останавливаются только тогда,
когда новые уже готовы их сменить.

Перед тем как обновлять скрипты `update.sh`/`rollback.sh`/
`docker-compose.prod.yml` на новую версию (если в самих скриптах тоже
что-то поменялось) — скачайте их заново тем же способом, что и при
установке:

```bash
cd /opt/attest0
curl -fsSL https://raw.githubusercontent.com/32syntax/attesto-deploy/main/docker-compose.prod.yml -o docker-compose.prod.yml
curl -fsSL https://raw.githubusercontent.com/32syntax/attesto-deploy/main/update.sh -o update.sh
curl -fsSL https://raw.githubusercontent.com/32syntax/attesto-deploy/main/rollback.sh -o rollback.sh
chmod +x update.sh rollback.sh
```

## 4. Откат обновления

Если после обновления что-то работает не так:

```bash
cd /opt/attest0
./rollback.sh
```

Без аргументов — откатывает **последнее** обновление: возвращает
предыдущую версию образов и восстанавливает базу данных из бэкапа,
который `update.sh` снял прямо перед тем обновлением.

Скрипт спросит подтверждение (`Продолжить? Введите 'да' для
подтверждения:`) и **прямым текстом предупредит**, что будет потеряно.

**Важно понимать, что откат — это не просто «вернуть старую версию
кода».** Он ещё и восстанавливает базу данных из бэкапа. Это значит:
всё, что пользователи сделали в системе **после** обновления и **до**
отката (новые тикеты в поддержку, результаты тестов, новые
пользователи, что угодно) — будет потеряно, база вернётся в состояние
на момент обновления.

**Если проблема не в данных, а просто в новой версии кода** (например,
что-то визуально сломалось, но никто ещё не успел ничего в новой
версии сохранить, или наоборот — вы уверены, что откатывать данные не
нужно, а нужно только вернуть код) — используйте вместо `rollback.sh`
обычное обновление на предыдущую версию, это **не трогает базу данных**:

```bash
./update.sh 0.24.2   # версия, на которой всё было хорошо
```

Это создаст новый бэкап перед откатом кода (текущих, актуальных
данных — не потеряется ничего), просто вернёт версию образов назад.
Разница с `rollback.sh`: `update.sh <старая версия>` не восстанавливает
БД из прошлого — использует её как есть, только применяет к ней
миграции (которые обратной совместимости ради не удаляют данные).
`rollback.sh` — это именно «отменить и код, и данные одним действием»,
для случаев, когда само обновление уже успело испортить данные.

## 5. Проверка, что всё работает

```bash
docker compose -f docker-compose.prod.yml --env-file .env ps
```

Все сервисы должны быть `Up`, у `backend` и `frontend` — `(healthy)`.

```bash
curl -s https://attest0.ru/api/v1/health
# {"status":"ok"}
curl -s https://attest0.ru/api/v1/ready
# {"status":"ready"}  — значит, есть подключение к базе данных
```

Логи конкретного сервиса (последние 100 строк, `-f` — непрерывно):

```bash
docker compose -f docker-compose.prod.yml --env-file .env logs backend --tail=100
docker compose -f docker-compose.prod.yml --env-file .env logs celery-worker --tail=100
docker compose -f docker-compose.prod.yml --env-file .env logs caddy --tail=100
```

## 6. Повседневные операции

**Ручной бэкап базы данных** (не только перед обновлением — например,
раз в сутки по cron):

```bash
cd /opt/attest0
mkdir -p backups
docker compose -f docker-compose.prod.yml --env-file .env exec -T db \
  pg_dump -U attesto -d attesto -F c > backups/manual_$(date -u +%Y%m%dT%H%M%SZ).dump
```

Пример строки в crontab (ежедневно в 03:00 UTC):

```
0 3 * * * cd /opt/attest0 && docker compose -f docker-compose.prod.yml --env-file .env exec -T db pg_dump -U attesto -d attesto -F c > backups/cron_$(date -u +\%Y\%m\%dT\%H\%M\%SZ).dump
```

**Перезапустить всё** (без потери данных — контейнеры пересоздаются,
volume с базой данных не трогается):

```bash
docker compose -f docker-compose.prod.yml --env-file .env restart
```

**Полностью остановить** (например, на время работ):

```bash
docker compose -f docker-compose.prod.yml --env-file .env stop
```

и снова поднять:

```bash
docker compose -f docker-compose.prod.yml --env-file .env up -d
```

**Никогда не выполнять на боевом сервере**, если не уверены на 100% —
это стирает данные:

```bash
docker compose down -v        # -v удаляет ВСЕ volume, включая базу данных
docker volume rm attest0_pgdata
```

## 7. Аварийный сценарий: скрипты не работают

Если `update.sh`/`rollback.sh` почему-то недоступны (например, файл
случайно удалили) — то же самое руками.

**Ручное обновление:**

```bash
cd /opt/attest0

# 1. Бэкап
docker compose -f docker-compose.prod.yml --env-file .env exec -T db \
  pg_dump -U attesto -d attesto -F c > backups/manual_before_update.dump

# 2. Новая версия в .env
sed -i.bak -e "s#^IMAGE_TAG=.*#IMAGE_TAG=0.24.3#" .env

# 3. Скачать образы и поднять
docker compose -f docker-compose.prod.yml --env-file .env pull
docker compose -f docker-compose.prod.yml --env-file .env up -d

# 4. Проверить
docker compose -f docker-compose.prod.yml --env-file .env ps
curl -s https://attest0.ru/api/v1/ready
```

**Ручной откат (восстановление базы данных из конкретного файла
бэкапа):**

```bash
cd /opt/attest0
ls -la backups/                       # выбрать нужный файл

# 1. Остановить backend и celery — чтобы никто не писал в базу во время восстановления
docker compose -f docker-compose.prod.yml --env-file .env stop backend celery-worker frontend

# 2. Восстановить (--clean стирает текущие данные перед восстановлением бэкапа)
docker compose -f docker-compose.prod.yml --env-file .env exec -T db \
  pg_restore -U attesto -d attesto --clean --if-exists < backups/ИМЯ_ФАЙЛА.dump

# 3. Вернуть версию образов, которая соответствует этому бэкапу, в .env
sed -i.bak -e "s#^IMAGE_TAG=.*#IMAGE_TAG=0.24.2#" .env

# 4. Поднять всё заново
docker compose -f docker-compose.prod.yml --env-file .env pull
docker compose -f docker-compose.prod.yml --env-file .env up -d
```

## 8. Частые проблемы

**`docker compose pull` пишет `denied`/`unauthorized`.** Образ ещё не
опубликован под этой версией, либо пакет в GitHub Container Registry
не публичный. Проверить версию на странице Releases; видимость пакета
(Package settings → Change visibility → Public) — в настройках
организации/аккаунта на GitHub, где собираются образы, делается один
раз после первой публикации.

**Сайт не открывается по HTTPS сразу после установки.** Caddy сам
получает сертификат Let's Encrypt при первом обращении — это может
занять 1-2 минуты и требует, чтобы DNS-запись домена уже указывала на
сервер. Логи: `docker compose -f docker-compose.prod.yml --env-file .env logs caddy --tail=50`.

**backend не проходит healthcheck после обновления.** Почти всегда —
незаполненный `.env` (SMTP/оплата, см. раздел 1) или ошибка в
миграции. Смотреть: `docker compose -f docker-compose.prod.yml --env-file .env logs backend --tail=100`.
Если не разобраться быстро — `./rollback.sh` возвращает рабочее
состояние, разбираться можно уже без спешки.

**Письма не приходят пользователям.** `EMAIL_BACKEND` в `.env` должен
быть `smtp` с реальными `SMTP_*`, не `console` (тот только пишет в
лог backend — годится для тестового стенда, не для боевого).
